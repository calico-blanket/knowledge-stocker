# LESSONS.md — このプロジェクトで得た教訓

## 2026-07-12 GASの新スコープはデプロイ時ではなく初実行時に承認される

- 症状: OAuthスコープ(documents/spreadsheets)を追加してWebアプリを再デプロイ・承認したのに、実機からの保存で「DocumentApp.createを呼び出す権限がありません」エラーが発生した。
- 根本原因: GASの権限承認は「そのスコープを実際に使うコードが初めて実行される」タイミングで要求されるが、Webアプリ(doPost)経由の実行では承認ダイアログを表示できず、静かに失敗する(証拠: エディタ上で `DocumentApp.create` を直接呼ぶ一時関数を実行したら承認画面が出て、以後は保存が成功した)。
- 教訓: GASに新しいサービス(スコープ)を追加したら、デプロイ手順に「エディタでそのサービスを直接呼ぶ関数を1回実行して承認を通す」を必ず含める。doGetのような何もサービスに触れない関数の実行では、必要な承認が出ないことがある。

## 2026-07-12 ユーザー環境の状態を推測で断定して誤案内した

- 症状: 「GAS再デプロイはもう一度必要か?」という質問に、時系列の推測だけで「はい、必要です」と断定して回答した。実際にはユーザーは既に最新コード(レビュー修正込み)をデプロイ済みで、再デプロイは不要だった。
- 根本原因: ユーザーがいつの時点のコードを貼り付けたかを観測せず、「私の修正より前のはず」という仮定を事実のように扱った(証拠: 同じ回答に書いた確認方法「sanitizeCellText_ の有無を検索」で、ユーザー自身が最新版デプロイ済みと判明)。
- 教訓: ユーザー環境の状態(デプロイ済みバージョン等)に依存する指示を出すときは、断定より先に識別子(そのバージョンにしか無い関数名・文言)による確認手順を提示する。fable原則2「主張ではなく観測を信じる」はユーザー環境にも適用する。

## 2026-07-12 初期実装(PWA+GAS)

- 症状: 実装一式のコミットを main へ直接 push した(グローバル CLAUDE.md の「main への直接 push はしない。作業はブランチを切る」に違反)。プロジェクト初期化指示の「初回コミットをプッシュ」に引きずられ、実装コミットもそのまま main で作業した。
- 根本原因: Phase 0 の「やらないこと」にグローバル Git 規約を転記しなかったため、突き合わせ対象から漏れた(証拠: git log で 4e54450 が main 直接コミット)。
- 教訓: Phase 0 で完了条件と一緒に「リポジトリ規約(ブランチ運用・push先)」を必ず1行で確認する。新規リポジトリでも2コミット目以降はブランチを切る。

## 2026-07-12 ヘッドレスChromeのスクリーンショット検証

- 症状: `chrome --headless --window-size=412,915 --screenshot` の画像で右列がはみ出して見え、CSSレイアウト崩れと誤診しかけた。
- 根本原因: このChromeでは `--window-size` がviewportに反映されず innerWidth=504 固定で描画され、画像だけが412幅に切り取られていた(証拠: `--dump-dom` で innerWidth=504 を実測)。
- 教訓: ヘッドレスのスクリーンショットで崩れを見つけたら、修復前にまず innerWidth を実測して撮影アーティファクトか裁定する。幅指定の検証は「指定幅のiframeに実ページを埋め込む」方式が確実。

## 2026-07-12 マージ済みブランチへの追加プッシュでPRから変更が漏れた(2回発生)

- 症状: ユーザーがPRをマージした後、同じブランチに次の変更をプッシュしたため、「PRをマージして」と案内しても該当変更が含まれておらず、ユーザーが「マージするものが見つからない」と混乱した。PR #1→#2間、PR #2→#3間で2回同じことが起きた。
- 根本原因: 「未マージのPRがあるブランチに積めばPRが育つ」という運用を、PRがマージ済みかを確認せずに続けた(証拠: gh pr view で state: MERGED のブランチに b2e5947 をプッシュしていた)。
- 教訓: プッシュ前に `gh pr view --json state` でそのブランチのPRの状態を確認する。マージ済みなら新しいブランチを切る。原則「1つの作業のまとまり=新ブランチ=1PR」で運用する。

## 2026-07-12 checkToken_の重複定義と、GET系APIの認可漏れ

- 症状: 全面レビューで、(1) `gas/Code.gs` に `checkToken_` が同一内容で2回定義されていた、(2) `doGet` の一覧・カテゴリAPIが合言葉ノーチェックで公開されていた、の2件を発見。どちらも数回のデプロイを経て本番に載っていた。
- 根本原因: (1) doPost周りをEditツールで大きく書き換えた際、新セクションに `checkToken_` を含めた一方で旧定義の削除を忘れた(証拠: 299行と349行に同一関数)。(2) 一覧APIを後付けした際「認可はPOSTで済んでいる」という思い込みがあり、GET側の保護を検討する工程自体がなかった(証拠: handleList_/handleCategories_ に checkToken_ 呼び出しが無かった)。
- 教訓: (1) 1ファイル内のセクション書き換え後は `grep -c "function 関数名"` で重複定義を機械チェックする(再発防止テストも追加済み)。(2) エンドポイントを追加するたびに「このAPIは誰が呼べるか・何が漏れるか」を1行で自問する。読み取り系は書き込み系より軽視しがちだが、漏れるのはむしろ読み取り系。

## 2026-07-12 Phase 0の明文化を追加タスクで省略した

- 症状: 初回のPWA+GAS新規構築では `/fable` を明示的に呼び出しPhase 0(完了条件・検証方法・やらないこと)を3行で提示してから着手したが、その後の追加タスク(Sheetsインデックス・カテゴリCRUD・URL解決・本文抽出・Google Docs化)では `/fable` を再度呼び出さず、Phase 0の明文化を省略したまま実装に入った。ユーザーから「直前のタスクのPhase 0を教えてください」と問われて初めて気づいた(証拠: 該当タスクの応答ログにPhase 0の3行提示が存在しない)。
- 根本原因: 「ユーザーが具体的な不具合を報告→即診断→即実装」という流れが速く、着手前に立ち止まって3行を書く手順が抜け落ちた。TodoWriteでのタスク分解とテストファーストは継続していたため、規律が完全に失われた自覚がなく、逸脱に気づきにくかった。
- 教訓: 同一セッション内で複数回に分けて機能追加が発生する場合、最初の `/fable` 呼び出し後も、ユーザーから新しい要望・不具合報告が来て次の実装に入る「その都度」Phase 0の3行(完了条件・検証方法・やらないこと)を再提示してから着手する。「診断が明確だから急いで直したい」という状況ほど、アンカーを飛ばしたくなるが、まさにそういう時こそ省略しやすいので注意する。

## 2026-08-02 ローカルの fetch 遅れを「引き継ぎ資料の誤り」と誤診しかけた

- 症状: Phase3着手時、`git log --oneline -10` の結果に Phase2 のマージコミットが無かったため、引き継ぎ資料の「Phase2はmainマージ済み」という前提が誤りだと報告しかけた。実際は GitHub 上では 2026-08-01T16:32:24Z にマージ済みで、ローカルの `origin/main` が2コミット古いだけだった(証拠: `git fetch origin` 後に `origin/main` が c515a80 → 21743ac へ進み、PR #2 のマージコミットが出現した)。
- 根本原因: ローカルの `git log` を「リモートの実状態」として扱った。`git log` が観測しているのは前回 fetch 時点のスナップショットであり、リモートの現在ではない。Phase2で「前提を鵜呑みにするな」という教訓を適用しようとした結果、逆に手元の古い観測を過信した。
- 教訓: 「マージ済みか」を判定するときは、必ず `git fetch` を先に実行してから `git log origin/main` を見るか、`gh pr list --state all --json state,mergedAt` でリモートに直接問い合わせる。ローカルの `git log` 単独ではブランチのマージ状態を判定しない。fable原則2「観測を信じる」は、その観測が何を写しているか(=いつの時点のリモートか)まで含めて確認して初めて成立する。

## 2026-08-02 インメモリスタブが実サービスの制約を再現しておらず、危険な仮定を見逃しかけた

- 症状: ID列(H列=8)追加時、テストのシートスタブは JS 配列の末尾拡張が自由にできるため、`getRange(1, 8)` が常に成功していた。しかし実の Google Sheets はシートの列数を超える `getRange` を範囲外エラーで拒否するため、余分な列を削除して運用しているシートでは移行が失敗しうる状態だった(証拠: スタブに列数上限を実装して `maxColumns: 7` のケースを足したところ、`ensureIndexColumns_` を外すとそのテストだけが失敗するようになった)。
- 根本原因: スタブは「テストが通ること」を基準に書かれており、実サービスの制約(既定26列・範囲外は例外)を再現していなかった。スタブ上で緑になったことを実環境の安全性の証拠として扱いかけた。
- 教訓: 外部サービスをスタブで置き換えているとき、「スタブが緑」は「実環境で動く」の証拠にならない。Phase 4 の「別レイヤーでの確認」では、スタブが実サービスの**制約(上限・例外・型)**まで再現しているかを1項目ずつ確認し、再現していない制約を見つけたらスタブ側に制約を足してから境界値を当てる。また、追加したテストがバグを実際に検出するかはミューテーション(意図的にコードを壊す)で確認する。
